# Развёртывание SPK.ctf-2026

Техническая инструкция для организатора. Этот каталог хранит **наши настройки и шаблоны**, но не является полной копией CTFd и не содержит состояние работающей базы данных.

> **Безопасность:** сервисы Web намеренно уязвимы. Запускайте их только в изолированной сети соревнования / через контролируемый VPN. Не публикуйте в открытый интернет. Репозиторий со всеми флагами и `solve.py` держите приватным до окончания соревнования.

## 1. Архитектура

- Linux VPS: `192.168.0.46` (адрес пример текущего стенда; при переносе замените).
- Локальный DNS Windows Server / Active Directory `labsec63.local`: запись `ctf.spk.ru → 192.168.0.46` (внутренняя зона `spk.ru`). Компьютеры должны использовать этот DNS.
- CTFd: Docker Compose из `~/spk-ctf/deploy/ctfd-app`; контейнер `ctfd` слушает 8000, Docker Nginx слушает 80 и 443.
- Участники: `https://ctf.spk.ru` → Nginx → `ctfd:8000`.
- Web-лаборатории: отдельный Compose в `~/spk-ctf/web/deploy`, порты 8001–8010. Crypto-оракулы: 8106 и 8109.
- Для временного удалённого администрирования использовался Tailscale; IP Tailscale не является публичным адресом участников.

## 2. Что хранится в Git

```
SPK-CTF-2026/
├── README.md
├── README_ORGANIZER.md
├── SPK_ctf_package.md
├── web/ crypto/ forensics/ stego/ reversing/
├── importer/
└── deploy/

    ├── ctfd-theme/
    │   ├── templates/base.html
    │   ├── css/spk.css
    │   ├── fonts/
    │   ├── img/
    │   └── pages/

```

Не коммитьте: `.env`, токены API, SSH/TLS-ключи (`*.key`, `*.pfx`, `*.p12`), настоящие пароли, дампы БД, резервные копии с пользователями и сессиями, а также каталоги CTFd с загруженными файлами. `*.cer`/`*.pem` можно хранить только после проверки, что это **публичный** сертификат без закрытого ключа; проще исключить их полностью.

## 3. Подготовка сервера

Установите Docker Engine с Compose plugin, Python 3, venv, Git, компилятор GCC/Make и утилиты, используемые заданиями. Для части артефактов нужны Pillow, reportlab, cryptography, steghide, exiftool, poppler-utils, zip/unzip, tshark и e2fsprogs. Версии зависимостей фиксируйте в отдельных requirements-файлах, когда они готовы.

Скопируйте исходники в `~/spk-ctf/`. Исходный CTFd нужно получать отдельно из официального репозитория в `~/spk-ctf/deploy/ctfd-app`, соблюдая версию, с которой тестировалась тема. **Не заменяйте весь каталог CTFd данными из этого репозитория.**

## 4. Восстановление темы CTFd

Пути исходной установки:

- `CTFd/themes/core/templates/base.html`
- `CTFd/themes/core/static/css/spk.css`
- `CTFd/themes/core/static/fonts/`
- `CTFd/themes/core/static/img/`

Скопируйте соответствующие файлы из `deploy/ctfd-theme/` в эти пути, предварительно сохранив резервные копии оригиналов. Проверьте относительные `url(...)` в `spk.css`, чтобы ссылки на изображения и шрифты были действительными. Скопируйте исходный HTML/Markdown страниц из `deploy/ctfd-theme/pages/` в CTFd Admin → Pages (`index`, `welcome`, `rules`) с правильным форматом страниц: эти страницы могут храниться в БД и не восстанавливаются простым копированием CSS.

## 5. DNS и HTTPS в изолированной сети

На Windows DNS заведите внутреннюю A-запись `ctf.spk.ru` на IP Linux VPS. Для HTTPS используется локальный AD CS (например, `LABSEC63-Root-CA`): выпустите сертификат **с SAN `DNS:ctf.spk.ru`** по CSR, созданному на VPS, чтобы закрытый ключ не уходил на Windows Server.

Сертификат и ключ храните **вне Git**. Пример `deploy/nginx/http.conf.example` адаптируйте к своему контейнеру Nginx и путям монтирования. Docker Compose должен публиковать 80:80 и 443:443, подключать `http.conf` и каталог с сертификатами; TLS обрабатывается Nginx, запросы проксируются на `ctfd:8000`. Для уведомлений CTFd сохраняйте отдельную конфигурацию `/events` с отключённым буферизованием. В CTFd используется `REVERSE_PROXY=true`.

Проверьте, что доверенный корневой сертификат CA распространяется на устройства участников и что CRL доступен в изолированной сети. Наличие HTTPS само по себе не гарантирует доверие браузеров. В идеале закройте прямой внешний доступ к порту 8000 после проверки обратного прокси.

## 6. Запуск сервисов

Запускать в **соответствующих** каталогах Compose, не объединяя автоматически разные `docker-compose.yml`:

```bash
cd ~/spk-ctf/deploy/ctfd-app
# Проверьте реальные пути volumes, secrets, .env и порты
# docker compose config -q
# docker compose up -d --build

cd ~/spk-ctf/web/deploy
# docker compose config -q
# docker compose up -d --build
```

Web-задания: `http://<IP_участников>:8001` … `:8010`; Crypto-оракулы: 8106/8109. Для изолированной сети используйте доступный участникам адрес, не частный Tailscale IP администратора. Уязвимые сервисы необходимо сетево изолировать от CTFd, AD и управляемых систем.

## 7. Генерация и проверка заданий

Не рассчитывайте на один универсальный `gen.py` во всех категориях: команды зависят от реально размещённых комплектов. В текущих пакетах организатора:

```bash
cd ~/spk-ctf/forensics && python3 gen_all.py && python3 verify_all.py
cd ~/spk-ctf/reversing && python3 verify_all.py
# для отдельных stego/crypto: python3 gen.py и verify.py/solve.py из каталога задания
cd ~/spk-ctf/web && python3 verify_all.py
```

Для Reverse при переносе на новую Linux-систему обязательно пересоберите ELF через Makefile: `for d in ~/spk-ctf/reversing/rev[0-9][0-9]_*/; do make -C "$d" clean && make -C "$d"; done`. Сверяйте флаги с **фактическими артефактами**, а не только с таблицей в Markdown; отдельные задания ранее меняли реализацию.

## 8. Импорт 50 заданий в CTFd

`importer/import_challenges.py` читает `SPK_ctf_package.md`, сопоставляет задания по категории/названию (с префиксами SPK-* и без), создаёт новые и обновляет имеющиеся. Имена на портале отображаются **без** `SPK-Crypto-09.` и подобных префиксов. Оценивание — `dynamic`, параметры Initial/Decay/Minimum по уровню сложности. Подсказки **сохраняются в документации, но не импортируются и не изменяются через API**.

CTFd данной сборки потребовал `Authorization: Token <token>` вместе с `Content-Type: application/json` даже для GET. Токен передавайте через переменную окружения, не записывайте его в репозиторий:

```bash
read -rsp 'CTFd API Token: ' CTFD_TOKEN; echo; export CTFD_TOKEN
cd ~/spk-ctf/importer
python3 import_challenges.py --root ~/spk-ctf --url http://127.0.0.1:8000 --host 192.168.0.46 --upload-files
# Изучить import_plan.json, проверить файлы, сделать резервную копию CTFd.
# Только после этого повторить команду с --apply.
```

Не перезаписывайте существующие вложения без проверки: скрипт пропускает уже привязанные имена файлов. После массового импорта новые задания могут быть hidden — опубликуйте их только после аудита. Не публикуйте организаторские `solve.py`, `gen.py`, `verify.py` и ключи в файлах заданий.

## 9. Резервирование, восстановление и передача проекта

- Перед изменениями CTFd: Admin → Config → Backup → Export. Резервные копии с пользователями храните **отдельно от GitHub**.
- Для воспроизводимости храните в Git исходники, документацию, собственную тему и *обезличенные* примеры конфигурации. Проверенные артефакты храните согласно политике размера репозитория.
- На другой сервер отдельно переносите секреты безопасным каналом и восстанавливайте БД/загруженные файлы из закрытых бэкапов, а не из Git.
- Перед соревнованием проверьте DNS, TLS/CRL, работоспособность всех 50 флагов, сетевую изоляцию, видимость заданий, отсутствие решений в выдаваемых файлах и актуальность ссылок.

## 10. Проверка перед GitHub

Перед `git add` проверьте `git status --short`, поиск ключей и токенов (не публикуйте найденные значения), вложенные `.git` и пользовательские данные. Проверьте лицензии шрифтов и графики. **Приватный GitHub** нужен, поскольку документация и исходники содержат решения всех 50 заданий.
